## 1. Sub-item columns in a file import — new in this push

**What was wrong.** On monday a sub-item belongs to a board of its own, with a column set of its own:
"שלב", "שעות", "קבלן" exist on the sub-items and nowhere on the parent board. The importer matched
sub-item columns to the parent's **by title** — which is what sharing a column means here — and
dropped every one with no counterpart. That is most of a sub-item board, so the sub-items arrived as
a list of names with every cell empty, over data that is plainly in the file: the export query
already asks for `subitems { column_values { column { title } … } }`.

**What changed.**

- A sub-item column the parent board has no counterpart for is created as a board column marked
  `sub_only`: it shows on the sub-item rows and never on the parent item, which is the structure the
  file describes. Created as an ordinary column it would stand on every item as well, empty forever.
- Its id is namespaced (`sub:<monday id>`). The two boards number their columns independently, so
  `status` on the sub-item board is not the parent's `status` — read by id, a sub-item's value landed
  in the wrong column.
- Sub-item columns are held to the rules the item columns are held to: a type with nothing to carry
  is skipped and named in the report, a column no sub-item filled is not a column of this board, and
  the board's column ceiling covers both sets together.
- A status column only the sub-items have keeps its vocabulary — the options are collected from the
  cells that reference them, so the labels and colours match instead of rendering grey.
- The import report names them ("N עמודות קיימות בתתי־הפריטים ולא בפריטי האב"), because the item row
  is where someone will look for them and not find them.

**The same loss in the xlsx/CSV importer.** The export names a sub-item-only column in the grey band
and not in the item header; the band's new columns were created board-wide. They are marked
`sub_only` now, and a header the items left empty while the sub-items filled it is no longer reported
as a column dropped for being empty.

**Frontend.** An empty shared subset (`sub_cols == ["item"]`) was read as "never configured — inherit
every item column". True for a stale list; wrong beside `sub_only` columns, which is a sub-item board
that shares nothing with its parent: it showed a dozen empty item columns in front of the ones that
are actually filled.

**What to re-test.** Import a monday response whose sub-items carry columns the parent board does not
have. Expected: the values are on the sub-item rows, those columns are absent from the item rows, and
the report lists them by name.

## 2. The board's history in an import, at board level and at item level

monday's `activity_logs` lands as the very rows this app's own log reads — `AuditLog` on the task — so
it appears in the item's own לוגים tab and in the board-level log at once. Nothing new was built to
display it; both views were already reading that table.

What was built is the part that does nothing: every log row offers a manager an undo, and undo writes
the old value back onto the item. An imported row describes something that happened in monday,
possibly a year ago, so that button would overwrite today's value with the board's past from a control
indistinguishable from every other undo. `AuditLog.origin` now marks a row's source and gates undo in
three places — `can_undo=false` from both activity endpoints, and `/api/activity/{id}/undo` refuses a
row that arrives anyway from a stale page. A change made here still undoes; the gate is about where
the row came from.

`origin` also keeps the author's name. monday names a person in its log only by a monday user id, so
the query asks for `users { id name email }` at the root. Matched to an account, the row is theirs;
unmatched, it keeps the name — "מערכת" over a change a named colleague made is worse than no history.

Rows naming an item or a column this import did not bring are counted and reported, not attached to
the nearest guess.

## 3. "טרם הוגדר" on the status and priority columns

A status or a priority can be put back to not-decided, from both pickers: the board's built-in columns
and a status column the board defined itself. The option is sized like the statuses beside it rather
than spanning the row, which is what the manage shortcut does — a grey button three times the width of
every status reads as something other than a value.

It travels as an explicit `null` plus `status_unset` / `priority_unset` in `custom_fields`, and any
board-defined label and colour the cell was carrying are cleared with it. The engine value stays
neutral (`todo` / `medium`) rather than becoming null, so the kanban can still group by it.

## 4. Status and priority changes in the log

The log was written from the `TaskStatus` and `Priority` enums, and a board does not speak in those: a
vocabulary maps onto them several entries to one, so moving an item between two statuses that share an
enum value wrote **no row at all**, and every board-defined status was logged as its base — a row
saying "תקוע" about an item somebody had put on "הקפאה". A log that reads as though only the original
status ever existed.

The row is now written from the vocabulary key the cell shows, once per column, after the whole edit
has landed. `/api/tasks/{id}/move` — the kanban drag, the sub-item status cell, the console `move`
command — audited nothing at all and left a board label behind in `custom_fields`, so the cell went on
painting a status the item no longer had; it goes through the board's vocabulary now and writes the
same single row. An automation's own `set_status` / `set_priority` is logged with no user behind it,
which both views render as "מערכת"; attributing it to whoever tripped the rule would be a lie about
who decided.

Undo learned the same vocabulary, and falls back to the engine value for a status the board has since
deleted and for rows written before this change.

A checkbox change reads as a tick in the log — a green `fa-square-check` or an empty `fa-square` —
instead of the word `true`.
